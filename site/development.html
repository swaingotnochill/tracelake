CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

Tradeoff: These guidelines bias toward caution over speed. For trivial tasks, use judgment.

1. Think Before Coding

Don't assume. Don't hide confusion. Surface tradeoffs.

Before implementing:

  • State your assumptions explicitly. If uncertain, ask.
  • If multiple interpretations exist, present them — don't pick silently.
  • If a simpler approach exists, say so. Push back when warranted.
  • If something is unclear, stop. Name what's confusing. Ask.
  • Do not edit code unless the user explicitly asks for implementation. If the user asks to "guide", "explain", "understand", "think through", or "start with defining" something, explain the design and Rust concepts step by step without changing source files.

2. Simplicity First

Minimum code that solves the problem. Nothing speculative.

  • No features beyond what was asked.
  • No abstractions for single-use code.
  • No "flexibility" or "configurability" that wasn't requested.
  • No error handling for impossible scenarios.
  • If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

3. Surgical Changes

Touch only what you must. Clean up only your own mess.

When editing existing code:

  • Don't "improve" adjacent code, comments, or formatting.
  • Don't refactor things that aren't broken.
  • Match existing style, even if you'd do it differently.
  • If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans:

  • Remove imports/variables/functions that YOUR changes made unused.
  • Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

4. Goal-Driven Execution

Define success criteria. Loop until verified.

Transform tasks into verifiable goals:

  • "Add validation" → "Write tests for invalid inputs, then make them pass"
  • "Fix the bug" → "Write a test that reproduces it, then make it pass"
  • "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

These guidelines are working if: fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

TraceLake is an open-source database purpose-built for LLM agent traces. It stores trace data in object storage (S3/GCS), uses NVMe/memory as hot cache, and beats generic databases (ClickHouse, Postgres, Elasticsearch) on trace-native workloads.

1. WHAT WE BUILD AND WHY

The Problem

LLM apps produce traces (spans). Each trace is a tree of spans — LLM calls, tool calls, retriever calls, agent decisions, eval scores. Teams store these in ClickHouse, Postgres, or Elasticsearch. None of these are built for traces:

  • ClickHouse: Great at analytics. Terrible at fetching one full trace (50-500ms). No native text search. Expensive replicated disks.
  • Postgres: Slow JSON handling (50-200ms per trace). No columnar analytics.
  • Elasticsearch: Expensive to operate. Not trace-native. Slow on joins/hydration.

The UI constantly needs "give me this entire trace tree." That's a point lookup with tree reconstruction — the opposite of what a column store is good at.

What TraceLake Does Differently

The storage unit is a trace pack (all spans for a trace_id grouped together), not a span row. Object storage is the source of truth. Compute is stateless. NVMe is disposable cache.

This means:

  • Fetching a full trace = one read, not a distributed row reconstruction.
  • Text search over prompts/outputs = native inverted index, not an external bolt-on.
  • Analytics = columnar scan over pre-built columns, not JSON extraction at query time.
  • Storage cost = S3 ($0.023/GB), not replicated EBS ($0.08-0.16/GB).

4. STEP-BY-STEP BUILD ORDER

Each step produces working, testable code. No step depends on a future step.

Step 1: tracelake-core — Data Types and Key Encoding

Build the Span struct, key encoding/decoding, and unit tests. No external dependencies beyond serde. This is pure data transformation.

Verify: key encode → key decode round-trips correctly for all span shapes. Benchmark: key encoding speed (target: >10M keys/s per thread).

Step 2: tracelake-ingest — SlateDB Integration

Open a SlateDB instance with InMemory object store. Write spans using the key encoding from Step 1. Read them back using scan_prefix().

Verify: write 100K spans, read them back grouped by trace_id. Benchmark: SlateDB put() throughput with our key pattern.

Step 2 Learning and Debugging Guide

The purpose of tracelake-ingest is to make hot trace writes real before any compaction or query engine exists. It should prove that a Span from tracelake-core can be encoded into the one canonical SlateDB key, written, and read back by trace prefix in deterministic order.

Build this crate in small, testable moves:

  1. Add one public write method, put_span(&amp;self, span: &amp;Span). Verify: one span writes without warnings and can be fetched by its exact key.
  2. Add one read method, get_trace_spans(...). Verify: scan the trace_prefix(...) and deserialize the returned values.
  3. Add one batch helper, put_spans(&amp;self, spans: &amp;[Span]). Verify: multiple spans from one trace read back sorted by start time.
  4. Add isolation tests. Verify: a trace prefix scan does not return spans from another trace, namespace, or tenant.
  5. Add the 100K span check only after the small tests pass. Verify: spans are grouped by trace_id and the count is exact.

While learning Rust, prefer explicit, idiomatic basics over clever code:

  • Use borrowed inputs for read-only APIs: &amp;Span, &amp;[Span], and &amp;str.
  • Return Result&lt;T, IngestError&gt; from every fallible public ingest function.
  • Use ? to propagate errors. Do not use unwrap() outside tests.
  • Use thiserror for error enums and preserve the source error with #[from].
  • Keep async only around SlateDB I/O. Serialization and key encoding are normal synchronous work.
  • Keep functions short. If a function handles key building, serialization, database I/O, and deserialization, split helper functions.
  • Add doc comments to every public struct and public function as the API appears.

Debug correctness before performance:

  • If writes fail, inspect the generated key first. Most ingest bugs will be bad tenant/namespace/trace/span identifiers or timestamp conversion.
  • If reads return nothing, compare the exact span key with the trace prefix. The span key must start with trace_prefix(tenant_id, namespace, trace_id).
  • If ordering is wrong, remember SlateDB sorts bytes lexicographically. The timestamp segment must stay zero-padded to the width defined in tracelake-core/src/key.rs.
  • If deserialization fails, print or inspect the stored value bytes in the test and confirm the value is the serialized Span, not the key.
  • If only root tests run, use cargo test --workspace. Plain cargo test at the repository root may not exercise every workspace crate.

Profile only after behavior is correct:

  • First use unit and integration tests to prove exact counts and grouping.
  • Then add a benchmark or ignored test that writes 100K spans with realistic tenant, namespace, trace_id, span_id, timestamps, and payload sizes.
  • Measure separate timings for key encoding, serialization, SlateDB put(), and scan_prefix() readback. A single total duration hides the bottleneck.
  • Do not claim ingest throughput until the benchmark discloses dataset shape, payload size, durability settings, and whether the object store is in-memory or S3-compatible.

Step 3: tracelake-compact — Trace Pack Writer

Read spans from SlateDB (sorted by key, which means grouped by trace_id). Write them into a trace pack binary format. Read the trace pack back and verify correctness.

Verify: write 10K spans (100 traces × 100 spans), read each trace back. Benchmark: trace pack write speed, trace pack read speed by trace_id.

Step 4: tracelake-compact — Full Segment Builder

Extend Step 3 to also write .bloom, .stats, .manifest. (Tantivy text index and Parquet columns come in later steps.)

Verify: build a segment, read it back, verify bloom filter catches non-existent traces. Benchmark: compaction throughput (spans/second).

Step 5: tracelake-query — Trace Fetch

Implement get_trace(): check SlateDB hot buffer first, then compacted segments. This is the merge path described in architecture.md.

Verify: write a trace, fetch it before compaction (hot), fetch it after compaction (cold). Benchmark: trace fetch latency (warm and cold).

Step 6: tracelake-query — Search

Implement search_traces() with status/model/time filters. Use bloom filters and stats for pruning.

Verify: write 1000 traces with various statuses, search for failed traces, verify correct. Benchmark: search latency with 10K/100K/1M traces in segments.

Step 7: tracelake-compact — Tantivy Text Index

Build Tantivy index during compaction. Store on object store. Query Tantivy index during search.

Verify: write traces with "hallucination" in output, text search finds them. Benchmark: text search latency, index build time.

Step 8: tracelake-query — Aggregation via DataFusion

Write .columns (Parquet) during compaction. Register custom TableProvider in DataFusion. Implement aggregate().

Verify: write traces with various latencies, compute p95 by model, verify correct. Benchmark: aggregation latency over 1M/10M/100M spans.

Step 9: tracelake-server — HTTP API

Wire up ingest, search, aggregate behind HTTP endpoints. Run end-to-end: ingest → compact → query.

Step 10: tracelake-bench — Full Benchmark Suite

tracelake-bench runs ingest, flush, hot and cold fetch, structural search, and text search phases over one synthetic corpus, printing dataset shape and correctness counts with each timing. Run it with cargo run --release -p tracelake-bench. Do not claim performance wins until the benchmark harness proves correctness, discloses dataset shape, and separates warm-cache, cold-cache, ingest, search, hydration, and freshness results.

Step 8 status

.columns Parquet files are written for every span and record segment. aggregate_spans and aggregate_records register those files in DataFusion and answer grouped count, sum, avg, min, max, and p50/p95/p99 queries. Filters are not pushed into aggregation yet.

Step 11: Custom Table Schemas and Eval Storage

Users define typed tables. Each table registers one schema per (tenant, namespace), validated on construction and again on load. A compatible change becomes the next schema version; record packs carry their own field descriptors, so older segments keep decoding. Records are validated at the ingest boundary, stored in the hot store under a record key family, compacted into typed record packs with per-field stats, and queried with typed filters, projection, and segment pruning. Eval runs from inspect-ai are stored as ordinary rows of the inspect_ai_samples table.

This step also implements Step 7: compaction builds a Tantivy index over span name, input, output, and error, and search_traces accepts text_query.

Reference: docs/schemas.md. Decision trail: docs/research/adr-custom-schemas.md.

Verify: register a schema, write records, query hot, compact, query cold with a filter that prunes segments, and ingest an inspect-ai log over HTTP.

4.1 IMPLEMENTATION PLAN ASSESSMENT

The initial plan is directionally good:

  • Object storage as source of truth matches SmithDB, Brainstore, and turbopuffer-style architecture.
  • Trace-local row storage is the right core bet for trace tree loads and hydration.
  • Separate columnar, text, bloom, stats, and manifest files match the actual workload mix.
  • Hot + compacted merge is required; both SmithDB and Brainstore optimize for realtime reads while background compaction catches up.
  • Rust, DataFusion, Tantivy, Parquet/Arrow, and stateless services are a reasonable stack.

Changes to make before implementation:

  • Treat SmithDB/Brainstore as the first-class benchmark competitors, not only generic ClickHouse/Langfuse/Elasticsearch systems.
  • Validate trace fetch and hydration on realistic large payloads early. A tiny synthetic span benchmark can hide the cost of deserializing prompts, outputs, and tool payloads.
  • Add thread filtering and tree-aware filters to the benchmark suite. SmithDB explicitly reports threads filtering, and agent observability workloads increasingly need it.
  • Measure read-after-write freshness as a benchmark. The design is incomplete if recent WAL/hot writes are fast to ingest but slow or inconsistent to query.
  • Do not make the MVP depend on reaching 1B spans first. Prove correctness and latency at 3.9M production-shaped traces, then scale to 50M traces / 1B spans.
  • Revisit the storage format choice after Step 3. FlatBuffers may be good for fixed fields, but huge semi-structured JSON payloads need a streaming/truncated preview path so UI lists do not fully deserialize multi-MB objects.

5. CODING RULES

DRY

  • One definition of the span schema. Used for ingest, storage, and query.
  • One key encoding function. Used for write and read.
  • One segment manifest format. Used by compactor and query planner.
  • If you write the same logic twice, extract it into a shared function immediately.

YAGNI

  • Do NOT build: user authentication, RBAC, multi-region replication, custom retention policies, vector search, SQL parser, admin UI, alerting integrations, export to CSV/JSON, GraphQL API, WebSocket streams.
  • Do NOT over-engineer: The query planner is a match statement, not an optimizer with cost models. The segment format is a flat binary file, not a self-describing container with version negotiation. The API is three endpoints, not a query language.
  • Build what's needed for Steps 1-10. Nothing more.
  • When in doubt, leave it out. We can always add it later.

Clean Code

  • Functions under 50 lines. If longer, split.
  • No magic numbers. Named constants for block sizes, thresholds, limits.
  • No implicit behavior. If a function can fail, return Result. If a parameter is required, don't make it Option.
  • Errors carry context. Use thiserror. Include what failed and why.
  • Tests for every public function. Tests for every edge case (empty traces, single-span traces, missing fields, duplicate span_ids).
  • No unwrap() in non-test code. Use ? or context().
  • Every pub fn has a doc comment. Every pub struct has a doc comment.
  • Async only where needed (I/O). CPU-bound work is synchronous.

6. WHAT WE DO NOT BUILD

To be explicit about scope boundaries:

  • We do NOT build a clickhouse replacement. We build a trace database.
  • We do NOT build a vector database. If semantic search is needed, add it later.
  • We do NOT build a log storage system. We store agent traces, not generic logs.
  • We do NOT build a real-time streaming system. CDC is a future optimization.
  • We do NOT build a schema registry. Attributes are opaque JSON.
  • We do NOT build SQL. The API is programmatic (search + aggregate structs).
  • We do NOT build multi-region replication. Object storage handles durability.
  • We do NOT build automatic scaling. That's a deployment concern, not a database concern.

7. OPEN QUESTIONS — ANSWER DURING PROFILING

These are NOT design decisions to make now. They are measurements to take during Steps 2 and 3. The answer determines whether we adjust, not whether we build.

  1. SlateDB throughput with our key size: Our keys are ~200 bytes (long prefixes). Does this hurt SlateDB's bloom filter efficiency or SSTable size? → Measure in Step 2.
  1. Trace pack optimal size: How large should each trace pack be? Too small = too many S3 objects. Too large = slow cold reads. → Measure in Step 3. Initial guess: 64-256 MB.
  1. Tantivy index size on S3: Tantivy indexes can be large relative to data. Does the text index fit in cache alongside trace packs and bloom filters? → Measure in Step 7.
  1. Hot/cold merge latency: How expensive is merging SlateDB hot buffer results with compacted segment results? Is it fast enough for real-time queries? → Measure in Step 5.
  1. Compaction keeping up with ingest: Can one compactor node keep up with 500K spans/s ingest? How many compactors do we need? → Measure in Step 4 after generating load in Step 2.

guild workflow

guild coordinates tasks (quest) and persistent knowledge (lore) across sessions and agents.

BEFORE ANY OTHER ACTION — before reading files, editing code, or responding to the user — call the MCP tool guild_session_start(project="tracelake"). It returns the full agent contract, active principles (oath), and the current top bounty. Follow what it returns.

If guild_session_start is not visible in your tool list, run your host's tool-search for guild first — some hosts lazy-load MCP tools. Do NOT fall back to CLI; the MCP server is available.

Core rules (full contract is returned by session_start)

  • Never use built-in task tools (TaskCreate / TaskUpdate / TaskList) — they're session-scoped. Use quest_post / quest_accept / quest_list instead.
  • Accept before working on a quest — quest_accept(quest_id=...) prevents parallel-agent collisions.
  • Appraise before researching — lore_appraise(query=..., all_projects=true) first. If current entries exist, use them.
  • Brief before session end — when wrapping up or compaction is near, call quest_brief("what was done, what's next, gotchas") without being asked.

MCP namespace: mcp__guild__*. CLI fallback: guild --help (last resort only).

10. VERIFICATION PROTOCOL

Full details and the coverage manifest: docs/verification.md.

  • Every pure function in tracelake-core and the pure query helpers (merge_spans, stats_may_overlap, span_matches, group_spans) is verification-covered: proptest properties, Kani proofs where reachable.
  • Before changing any of them: run cargo test --workspace plus cargo kani -p tracelake-core -p tracelake-query.
  • New pure functions in those modules require a property test (and a Kani harness when reachable) in the same change.
  • Bug fixes in verified code require a failing property first, committed with the fix; commit any generated *.proptest-regressions seed files.
  • Never delete or weaken a property to make verification pass.
  • SlateDB, tokio, axum, serde, chrono, crc32fast are trusted boundaries — never describe behavior behind them as "verified".
