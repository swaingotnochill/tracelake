TraceLake Verification Protocol

This document defines what "verified" means in TraceLake, what is covered, how to run the verification suite, and the rules any contributor — human or AI agent — must follow when changing verified code.

Companion research: formal-verification-brief.md (tool selection), rocq-of-rust-assessment.md (rejected alternative), fv-implementation-report.md (first results).

1. The three tiers

Every operation we own sits in exactly one tier. A claim of "verified" must always name the tier.

TierMeaningToolsTrust level
PROVENHolds for all inputs within documented bounds (loop unwinds). No panic, no UB, functional law.Kani (#[cfg(kani)] mod verify in the source file)Highest — counterexample-free by construction
PROPERTYHolds for hundreds of randomized, shrunk cases; regressions are pinned via committed seed files.proptest (tests/prop_*.rs, src/search/verification.rs)High — bugs in practice
INTEGRATIONBehavior checked end-to-end on concrete scenarios.#[tokio::test] suites + router-level HTTP testsNormal test trust

Statistical properties (e.g. bloom FPR ≤ 2× target) are PROPERTY tier with explicitly generous margins; they cannot be proven, only bounded.

2. Trusted boundaries (NOT verified, by design)

SlateDB, tokio, axum, object_store, serde/serde_json internals, crc32fast, and chrono internals are assumptions. No proof crosses into them. The async orchestration (get_trace/search_traces flows, compactor I/O, server handlers) is INTEGRATION tier: its pure decision logic is extracted and verified (see manifest), its I/O choreography is tested.

If SlateDB returns a span scan_prefix did not store, no proof we write catches that. That is the boundary, stated plainly.

4. How to run

cargo test --workspace                     # everything incl. proptest suites (seconds)
cargo kani -p tracelake-core               # PROVEN tier, core (minutes)
cargo kani -p tracelake-query              # PROVEN tier, merge and prune laws
cargo kani -p tracelake-core --harness field_type_tags_round_trip
cargo kani -p tracelake-query --harness ge_prune_means_the_segment_max_is_below_the_bound
cargo clippy --workspace --all-targets -- -D warnings

CI runs the same: check job on every PR; a Kani job when tracelake-core/** or tracelake-query/** changes; Miri (nightly, non-blocking) on tracelake-core.

5. Agent / contributor protocol (mandatory)

  1. Changing a pure function in tracelake-core or the pure helpers in tracelake-query (merge.rs, stats_may_overlap, span_matches, summarize_trace, group_spans): run cargo test --workspace AND the relevant cargo kani -p … before committing. If you cannot run Kani, say so in the commit message — do not claim PROVEN tier.
  2. New pure function in those modules: add a proptest property and, where Kani can reach it, a #[cfg(kani)] harness in the same file. Update the manifest in §3.
  3. Bug fix in verified code: first add the failing property (proptest or Kani assertion) that reproduces the bug, then fix, then commit both together. The proptest seed file this generates must be committed.
  4. Reading failures:
  5. proptest prints a shrunk counterexample and writes a seed to *.proptest-regressions; rerun with PROPTEST_SEED=&lt;seed&gt; to reproduce deterministically.
  6. Kani failures show a trace to the violating input; "unwinding assertion" means raise #[kani::unwind(N)] or restructure the loop — never delete the property to make it pass.
  7. Never widen a margin, bound, or assume to make verification pass without a written justification in the harness comment.
  8. Keep harness strings fixed and small; symbolic Strings explode solver time. Symbolic numerics with kani::assume bounds are the pattern (see key.rs::verify).

6. Known verification debts

  • stats_may_overlap Kani proof pending an i64-nanosecond core extraction (chrono boundary) — PROPERTY tier until then.
  • Solver-cost reality: harnesses over format!/std-parse/serde_json/OS-seeded hashing are restructured to verification cores (pure byte/int functions) — this is deliberate, not a coverage cut. Remaining heavy solves (timestamp round-trip/ordering, merge L3/L4, pack corruption) run in the CI kani job on x86_64; local Apple-Silicon CBMC is several times slower.
  • Fuzzing (cargo-fuzz targets over the three parsers) and Miri CI are planned; Miri is insurance — the codebase has no unsafe today.
  • summarize_trace deserves direct PROPERTY-tier coverage once search summaries stabilize.
  • Text search over the hot store builds an index per query. It is correct but not benchmarked.
  • Aggregation accepts no filter yet. A filtered aggregate reads every column file for the table.
  • The span and record Kani harnesses are the only decoder proofs; the DataFusion SQL generation and Parquet writing are INTEGRATION tier.
  • The record pack Kani harness (record_pack.rs::verify) exists and the kani workflow runs it. A local run exceeded 30 minutes on Apple Silicon, so the decoder stays PROPERTY tier until that CI job reports green.
  • Record-query pruning is sound while the hot store keeps the newest copy of every record. If SlateDB starts dropping compacted hot data, a pruned segment could return a stale version. See adr-custom-schemas.md.
